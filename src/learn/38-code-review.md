# 用 Codex 做代码 Review

代码 Review 是审查一组改动是否引入问题。它和“把代码写得更好看”不同，首先关注功能错误、兼容性、数据影响和缺失验证。

## 先指定审查范围

可以审查未提交改动、某个提交，或某个分支相对基线的差异。不要只说“检查整个项目”，却没有说明本次改了什么。

```text
请只审查当前未提交改动，不修改文件。
重点检查功能回归、错误处理、边界条件和测试缺口。
发现问题时，说明文件位置、触发条件、影响和依据。
按影响排序；不确定的地方列为待确认，不把个人风格偏好当成 Bug。
```

## 怎样判断反馈有价值

假设样式修改将按钮设为固定宽度，手机上可能溢出。好的反馈会说明规则位置、触发宽度和实际影响；“响应式不够好”则过于笼统。

一个问题最好能回答三句话：什么情况下发生，用户会看到什么，为什么与本次改动有关。

## Review 后怎么处理

逐条复现重要问题，确认后再安排修复。不要让审查同时大范围重构，否则很难分清哪些是必要修复、哪些是新引入的变化。

修复后重新检查相关差异和验证结果。没有发现问题不等于保证没有问题；如果没有运行测试或无法预览，要记录这个限制。

**完成标准：** 每个有效结论都有位置、证据和影响，报告同时说明审查范围及未验证内容。
