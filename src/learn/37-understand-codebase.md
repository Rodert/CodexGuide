# 用 Codex 阅读项目

接手项目时，不必先逐行读完所有代码。先建立一张小地图：入口在哪里、核心流程是什么、怎样运行，以及哪里需要进一步确认。

## 第一轮：只看结构

第一次可以使用 [个人网页包](/examples/personal-page.zip)，解压后打开其中的项目目录。先不选择复杂仓库，发送：

```text
先只读，不修改文件，不安装依赖。
阅读 README、目录和依赖声明，说明：
1. 这是什么项目，主要技术是什么。
2. 页面或服务入口在哪里。
3. 核心目录各自负责什么。
4. 如何启动和测试，依据来自哪些文件。
把确认事实和推测分开，不要扫描生成目录或依赖源码。
```

解释每个目录都用一句话即可。先把项目看清楚，再决定要深入哪个模块。

这个包的合理结论很简单：`index.html` 放内容，`style.css` 放样式，通过 HTML 的 `link` 引用关联；浏览器直接打开 HTML 即可。它没有依赖声明和后端，报告应如实说明，不应编出数据库、接口或构建命令。

## 第二轮：追踪一条真实流程

个人网页可以追踪“点击联系按钮到打开邮件应用”；后端项目可以追踪“请求进入路由到数据库查询”。

继续要求：

```text
沿着一个具体功能说明调用顺序，给出相关文件和函数位置。
如果跳转到外部库，说明边界，不要猜测内部行为。
```

通过文件位置抽查结果。函数名正确，不代表调用关系一定正确；特别注意同名函数、测试代码和已经不用的旧实现。

实际跟练可以让它指出联系按钮的 HTML 位置，自己打开文件核对 `mailto:` 地址。文件和页面能一一对应后，再把同样方法用于真实项目。

## 第三轮：验证运行方法

先看启动命令和依赖是否明确，再决定是否安装、运行。未知仓库里的脚本可能有真实副作用，不要把“阅读项目”直接扩大成部署或数据库迁移。

**交付结果：** 一份简短项目地图、一条功能流程、启动方法及待确认问题。需要长期保存时，把核实后的内容整理进项目文档。
