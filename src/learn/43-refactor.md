# 重构代码模板

重构主要改变内部结构，保持对外行为。它不应悄悄变成新增功能、修改接口或切换技术栈。

## 先说清要改善什么

“优化代码”没有明确终点。改成“消除两个函数中的重复校验逻辑，保持返回值和异常行为不变”，才能检查是否完成。

```text
请重构 [文件或模块]。

问题：[重复逻辑、职责混乱或难以理解的位置]
目标：[希望改善的具体结构]
保持不变：[接口、返回值、异常、顺序和兼容范围]
限制：[不新增依赖、不修改数据结构等]

先阅读现有实现和相关测试，说明行为边界。
测试不足时，先补充关键行为的验证，再逐步重构。
不要顺手修改无关命名或格式，不改变公共接口。
完成后报告结构变化、兼容性检查和未覆盖风险。
```

## 怎么验收重构

用 [JavaScript 练习包](/examples/js-practice.zip) 具体操作：

1. 解压，在项目目录执行 `npm test`，先确认初始 1 个用例通过。
2. 打开 `tasks.js`，它有两段相似循环，分别统计已完成和待完成任务。
3. 把模板中的问题填为“整理两段计数循环”，要求保留 `done === true` 的定义，不修改输入、不增加依赖。
4. 让 Codex 先补关键行为检查，再重构并重新运行测试。

需要更明确的用例时先完成 [补测试练习](./45-add-tests.md)。最终空数组、全部完成以及没有 `done` 的对象，都应保持约定结果。

看差异是否围绕原问题展开，再用原有调用方式检查输入、输出和异常。仅仅“编译通过”不一定覆盖行为变化。

如果重构把判断从 `done === true` 改成 `if (done)`，字符串等非布尔值的处理也可能改变。即使代码更短，也要按原约定检查，而不能直接接受。

网页项目中，可以整理重复样式，但要对照宽窄屏效果。没有自动化测试时，也应记录手工检查过的场景。

## 避免一次改太多

重构和功能变更尽量分别完成，方便判断回归来自哪里。发现原实现存在 Bug，可以单独记录，再决定是否扩展本次范围。
