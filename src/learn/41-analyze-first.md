# 先分析再修改

不确定功能在哪里实现，或者担心修改影响太大时，先让 Codex 调查。分析阶段的产物是证据与方案，不是已经改好的文件。

## 第一阶段：只读分析

```text
先分析，不修改文件，不安装依赖，不启动有写入副作用的任务。

目标：[想解决的问题]
现象：[实际观察]
已知线索：[文件、日志、发生时间或操作步骤]

请说明：
1. 相关文件与当前工作流程。
2. 已确认的事实、可能原因和缺失信息。
3. 最小修改方案、影响范围和验证方法。
不确定时先说明，不把猜测写成结论。
```

例如，“网页布局不好”太宽泛；“窗口缩到 375 像素时作品卡片超出页面”更容易定位。

## 第二阶段：按选定方案执行

看完分析，再发送：

```text
按刚才的最小方案执行，只处理已确认的问题。
保留其他改动，不扩大重构范围。
如果发现前提不成立或需要新增依赖，先说明变化。
完成后对照原始复现步骤验证，并报告结果。
```

## 如何判断分析是否足够

你应该能回答“改哪里、为什么、影响什么、怎么验证”。仅有技术术语、没有文件位置和证据，不足以支持修改。

这个流程适合陌生项目、影响较大的变更和原因不明的错误。简单文案修改不必强行分成多轮，流程要与任务大小相称。
