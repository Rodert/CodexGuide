# 停止、回退与恢复

任务走偏时先停止，再检查。停止对话、停止进程和撤销文件改动是三件事；其中一个完成，不代表其他两个也已经完成。

## 第一步：确认停止了什么

使用当前入口的停止操作后，检查是否还有终端命令、预览服务或后台任务运行。取消生成不会自动恢复已经写入的文件，也不会撤销已经发出的外部请求。

## 第二步：查看实际状态

Git 项目中先执行：

```bash
git status --short
git diff
git diff --cached
```

它们分别帮助查看文件状态、未暂存差异和已暂存差异。新增但未跟踪的文件通常不会显示在普通 Diff 中，所以要结合状态列表检查。

## 第三步：选择恢复方式

| 状态 | 处理思路 |
| --- | --- |
| 未提交改动 | 对照差异，只撤销明确属于错误任务的部分 |
| 已提交但未推送 | 确认是否要保留历史，再选择恢复方式 |
| 已推送或多人共享 | 通常优先用新提交撤销错误，避免改写共享历史 |
| 已部署或修改外部数据 | 需要对应系统的回滚或恢复流程，Git 不能全部撤销 |

不要把“恢复之前的样子”理解成清空所有改动，尤其同一个文件可能同时包含你和 Codex 的修改。

## 可以这样要求协助

```text
先检查当前文件和 Git 差异，不执行删除或重置。
识别本次任务引入的改动，保留其他工作。
列出可恢复的部分、无法安全区分的部分及建议方法。
确认恢复范围后再执行，完成后重新检查差异。
```

第一次恢复练习可以很小：先按 Git 教程保存正常网页，确认状态干净；只把页面标题改成“撤销练习”，看到变化后，再要求 Codex“只把这次标题恢复为上一版文字，保留其他内容”。刷新并检查差异，确认没有误删新文件或其他修改。

这个练习只恢复一处内容，不需要清空整个工作区。真实任务中若同一文件混入多个人的改动，先逐段核对，无法区分的部分不要直接丢弃。

没有版本、备份或副本时，部分内容可能无法可靠恢复。养成小步提交习惯，比出错后寻找万能撤销命令更实用。
